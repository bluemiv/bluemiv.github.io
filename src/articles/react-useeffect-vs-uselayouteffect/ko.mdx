`useEffect`와 `useLayoutEffect`는 모두 React가 DOM을 갱신한 뒤 실행돼요. 가장 큰 차이는 effect가 브라우저의 화면 그리기를 막는지에 있어요.

대부분의 작업에는 `useEffect`가 맞아요. DOM의 크기나 위치를 측정하고 그 결과를 첫 화면이 보이기 전에 반영해야 할 때만 `useLayoutEffect`를 선택하는 편이 안전해요.

## 한눈에 비교하기

| 기준 | `useEffect` | `useLayoutEffect` |
| --- | --- | --- |
| 주된 목적 | 외부 시스템과 상태 동기화 | paint 전 DOM 측정과 시각적 보정 |
| 실행 시점 | commit 이후, 대체로 paint 이후 | commit 이후, paint 이전 |
| browser paint 차단 | 차단하지 않음 | effect와 내부 state update가 끝날 때까지 차단 |
| 대표 사례 | event listener, timer, 외부 widget, network 연결 | tooltip 위치, element 크기 측정, scroll 위치 보정 |
| server rendering | 실행되지 않음 | 실행되지 않으며 server에는 layout 정보가 없음 |
| 기본 선택 | 우선 사용 | 꼭 필요한 시각적 작업에만 사용 |

두 Hook은 dependency와 cleanup 규칙이 같아요. dependency가 바뀌면 이전 cleanup을 먼저 실행하고 새로운 setup을 실행해요. 컴포넌트가 제거될 때도 마지막 cleanup이 실행돼요.

## React render, commit, paint 흐름

실행 시점을 정확히 이해하려면 React의 render와 commit을 구분해야 해요.

1. **Render**: React가 컴포넌트를 호출해 화면에 무엇을 표시할지 계산해요.
2. **Commit**: 계산 결과를 실제 DOM에 반영해요.
3. **Paint**: 브라우저가 변경된 DOM과 style을 화면의 pixel로 그려요.

effect까지 포함해 단순화하면 다음 순서예요.

```text
render
→ commit (DOM update)
→ useLayoutEffect
→ browser paint
→ useEffect (일반적인 경우)
```

`useLayoutEffect`는 DOM이 갱신된 다음 실행되므로 element를 측정할 수 있어요. React는 이 안의 코드와 state update를 처리한 뒤 브라우저가 화면을 그리도록 보장해요.

반면 `useEffect`를 무조건 paint 뒤에 실행되는 Hook으로 이해하면 정확하지 않아요. React는 interaction으로 발생하지 않은 effect라면 대체로 브라우저가 먼저 화면을 그리게 해요. 클릭 같은 interaction에서 시작된 effect는 event system이 결과를 관찰할 수 있도록 paint 전에 실행될 수도 있어요. 실행 순서 자체보다 **paint를 반드시 막아야 하는가**를 선택 기준으로 삼는 편이 좋아요.

`useLayoutEffect`는 동기, `useEffect`는 비동기라고만 외우는 것도 정확하지 않아요. 두 setup 함수가 자동으로 동기 함수와 비동기 함수가 되는 것은 아니에요. React가 commit과 paint를 기준으로 effect를 언제 처리하는지, 그 과정에서 paint를 차단하는지가 핵심 차이예요.

## useEffect를 사용하는 경우

`useEffect`는 React 바깥의 시스템과 컴포넌트를 동기화할 때 사용해요. browser event, timer, network connection, third-party widget처럼 React가 직접 관리하지 않는 대상이 여기에 해당해요.

아래 컴포넌트는 `Escape` key event를 구독하고, 컴포넌트가 사라지거나 `onEscape`가 바뀌면 기존 listener를 정리해요.

```tsx
import { useEffect } from "react";

type PropsWithEscapeKeyListener = {
  onEscape: () => void;
};

export function EscapeKeyListener({ onEscape }: PropsWithEscapeKeyListener) {
  useEffect(() => {
    function handleKeyDown(event: KeyboardEvent) {
      if (event.key === "Escape") onEscape();
    }

    window.addEventListener("keydown", handleKeyDown);

    return () => {
      window.removeEventListener("keydown", handleKeyDown);
    };
  }, [onEscape]);

  return null;
}
```

이 작업은 다음 paint 전에 끝나야 할 이유가 없어요. `useLayoutEffect`로 바꾸면 같은 결과를 만들면서도 browser paint를 불필요하게 막게 돼요.

API 요청도 client에서 직접 처리해야 한다면 `useEffect`를 사용할 수 있어요. 다만 Next.js 같은 framework에서는 server data fetching, route loader, cache library를 먼저 검토하는 편이 좋아요. effect에서 직접 요청할 때는 컴포넌트가 사라지거나 dependency가 바뀐 뒤 이전 응답이 state를 덮어쓰지 않도록 cleanup도 함께 설계해야 해요.

## useLayoutEffect가 필요한 경우

`useLayoutEffect`는 DOM을 측정한 결과가 첫 화면에 반영돼야 할 때 필요해요. 대표적인 사례는 tooltip이나 popover의 위치 계산이에요.

아래 tooltip은 target과 자신의 크기를 측정한 뒤 target 위에 배치해요. 화면 위쪽에 공간이 부족하면 아래쪽으로 내려가요.

```tsx
import type { ReactNode } from "react";
import { useLayoutEffect, useRef, useState } from "react";

type PropsWithTooltip = {
  children: ReactNode;
  target: HTMLElement | null;
};

type Position = {
  left: number;
  top: number;
};

export function Tooltip({ children, target }: PropsWithTooltip) {
  const tooltipRef = useRef<HTMLDivElement>(null);
  const [position, setPosition] = useState<Position | null>(null);

  useLayoutEffect(() => {
    if (!target || !tooltipRef.current) return;

    const targetRect = target.getBoundingClientRect();
    const tooltipRect = tooltipRef.current.getBoundingClientRect();
    const top = targetRect.top - tooltipRect.height - 8;

    setPosition({
      left: targetRect.left + (targetRect.width - tooltipRect.width) / 2,
      top: top >= 8 ? top : targetRect.bottom + 8,
    });
  }, [target]);

  return (
    <div
      ref={tooltipRef}
      role="tooltip"
      style={{
        position: "fixed",
        left: position?.left ?? 0,
        top: position?.top ?? 0,
        visibility: position ? "visible" : "hidden",
      }}
    >
      {children}
    </div>
  );
}
```

처리 과정은 두 번의 render로 이루어져요.

1. 위치를 모르는 상태로 tooltip을 DOM에 반영해요.
2. `useLayoutEffect`에서 실제 크기와 위치를 측정해요.
3. 측정 결과를 state에 저장하고 즉시 다시 render해요.
4. 브라우저는 최종 위치의 tooltip만 화면에 그려요.

같은 코드를 `useEffect`에 넣으면 브라우저가 초기 위치를 먼저 그릴 수 있어요. 이후 측정한 위치로 이동하면서 tooltip이 순간적으로 튀거나 깜빡여 보일 수 있어요.

다만 CSS만으로 위치를 결정할 수 있거나 첫 frame의 변화가 사용자에게 보이지 않는다면 `useEffect`도 충분해요. DOM을 읽는다는 이유만으로 `useLayoutEffect`를 선택할 필요는 없어요.

위 예제는 두 Hook의 차이를 보여주기 위해 초기 배치만 다뤄요. 실제 tooltip은 viewport resize, scroll, 내용 크기 변경까지 반영해야 하므로 검증된 positioning library나 `ResizeObserver` 같은 browser API도 함께 검토해야 해요.

## useLayoutEffect를 피해야 하는 이유

`useLayoutEffect` 안의 코드와 그 안에서 발생한 state update는 browser paint를 막아요. 여기에서 큰 DOM tree를 반복해서 측정하거나 오래 걸리는 연산을 실행하면 첫 화면과 interaction 반응이 늦어져요.

```tsx
useLayoutEffect(() => {
  const startedAt = performance.now();

  while (performance.now() - startedAt < 1000) {
    // 이 작업이 끝날 때까지 browser paint가 지연돼요.
  }
}, []);
```

이런 계산은 `useEffect`로 옮긴다고 자동으로 효율적이 되지는 않아요. render에 필요한 순수 계산은 render 단계에서 처리하고, 비용이 큰 계산은 memoization이나 worker 같은 별도 전략을 검토해야 해요. `useLayoutEffect`에는 측정과 즉시 필요한 최소한의 state update만 남기는 편이 좋아요.

## 테마와 redirect에는 무엇을 써야 할까?

화면 깜빡임을 막는다는 이유로 모든 style 변경이나 redirect에 `useLayoutEffect`를 적용하면 안 돼요.

### 초기 테마

server rendering을 사용하는 화면은 JavaScript가 load되고 hydration이 끝나기 전에 HTML이 먼저 보일 수 있어요. `useLayoutEffect`는 server에서 실행되지 않으므로 초기 theme 깜빡임을 완전히 해결하지 못해요.

초기 theme은 CSS의 `prefers-color-scheme`, server가 만든 HTML class, 또는 hydration 전에 실행하는 짧은 초기화 script로 맞추는 편이 안전해요. 사용자가 theme button을 누른 뒤 DOM class를 바꾸는 동작은 event handler에서 직접 처리할 수 있어요.

### Redirect와 접근 제어

redirect는 router나 framework의 route 단계에서 처리하는 것이 우선이에요. 특히 로그인 여부처럼 접근 제어와 관련된 판단은 server나 middleware에서 검증해야 해요. `useLayoutEffect`로 화면을 가린 뒤 이동하는 방식은 보안 경계가 될 수 없어요.

client에서만 알 수 있는 값으로 이동해야 한다면 `useEffect`와 조건부 render를 함께 사용할 수 있어요. 이때 이동 전까지 보호해야 하는 내용을 JSX에 포함하지 않는 것이 중요해요.

## SSR과 Next.js에서 주의할 점

`useEffect`와 `useLayoutEffect`는 모두 client에서만 실행돼요. Next.js App Router에서 두 Hook을 사용하는 컴포넌트에는 client component 경계가 필요해요.

server에는 viewport와 element 크기 같은 layout 정보가 없어요. 따라서 server에서 만든 첫 HTML이 `useLayoutEffect`의 측정 결과에 의존한다면 hydration 후 위치가 바뀌거나 경고가 생길 수 있어요.

이 문제가 생기면 다음 순서로 검토해요.

1. layout 측정 없이 CSS로 해결할 수 있는지 확인해요.
2. 첫 화면에 측정 결과가 필요하지 않다면 `useEffect`로 바꿔요.
3. interaction 이후에만 필요한 tooltip처럼 server HTML에 없어도 되는 UI는 client에서 열릴 때 render해요.
4. client 전용 UI라면 안정적인 placeholder를 제공해 layout shift를 줄여요.

개발 환경의 Strict Mode에서는 두 Hook 모두 첫 setup 전에 `setup → cleanup → setup` 과정을 한 번 더 실행할 수 있어요. effect가 두 번 실행되는 것처럼 보인다면 Hook을 바꾸기보다 cleanup이 setup을 정확히 되돌리는지 먼저 확인해야 해요.

## 선택 기준

effect를 작성하기 전에 아래 순서로 판단하면 대부분의 경우를 정리할 수 있어요.

1. React 바깥의 시스템과 동기화하지 않는다면 effect가 필요하지 않은지 먼저 확인해요.
2. event listener, timer, network connection, 외부 widget 연동이라면 `useEffect`를 사용해요.
3. DOM을 측정한 결과를 첫 paint 전에 반영해야 하고 실제로 깜빡임이 보인다면 `useLayoutEffect`를 사용해요.
4. CSS, router, framework 기능으로 해결할 수 있다면 effect보다 그 방법을 우선해요.
5. `useLayoutEffect`를 선택했다면 실행 시간을 짧게 유지하고 layout read와 write를 반복하지 않아요.

결론은 단순해요. **기본은 `useEffect`이고, paint 전에 끝나야 하는 layout 측정만 `useLayoutEffect`로 옮겨요.** 두 Hook의 이름보다 사용자에게 잘못된 첫 frame이 보이는지, 그리고 paint를 막을 이유가 있는지를 기준으로 판단하는 편이 정확해요.
