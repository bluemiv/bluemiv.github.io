LLM은 학습한 지식을 바탕으로 자연스러운 답변을 만들지만, 사내 문서처럼 학습에 포함되지 않은 정보나 자주 바뀌는 정책까지 항상 알고 있지는 않아요. 모르는 내용을 그럴듯하게 만들어 낼 수도 있고, 답변의 근거가 어디에서 왔는지 확인하기도 어려워요.

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 질문과 관련된 외부 자료를 먼저 검색하고, 검색 결과를 LLM의 context에 넣어 답변을 생성하는 방식이에요. model을 다시 학습하지 않고도 새로운 정보를 반영할 수 있고, 출처를 함께 제공해 답변을 검증하기 쉬워진다는 장점이 있어요.

다만 vector database를 연결한다고 RAG가 완성되는 것은 아니에요. 문서를 어떻게 나누고, 무엇을 검색하며, 어떤 결과만 LLM에 전달할지에 따라 품질이 크게 달라져요.

RAG가 hallucination을 없애 주는 것도 아니에요. 잘못된 문서를 찾거나 LLM이 주어진 근거를 제대로 사용하지 않으면 여전히 틀린 답을 만들 수 있어요. 그래서 retrieval과 generation을 분리해서 관찰하고 평가해야 해요.

## RAG가 필요한 이유

LLM이 가진 지식은 model parameter 안에 저장돼요. 이를 parametric memory라고 불러요. 한 번 학습된 정보는 즉시 고치기 어렵고, 특정 답변이 어떤 원문에서 나온 것인지 추적하기도 쉽지 않아요.

RAG는 문서 저장소나 검색 index를 별도의 non-parametric memory로 사용해요. 질문할 때마다 필요한 자료를 검색하므로 지식이 바뀌면 문서와 index만 갱신할 수 있어요. 권한이 있는 내부 문서, 제품 설명서, 고객 지원 기록처럼 model training에 넣기 어려운 자료도 다룰 수 있어요.

2020년 발표된 RAG 논문은 생성 model의 parametric memory와 Wikipedia의 dense vector index를 결합했어요. 여기서 중요한 발상은 model이 모든 사실을 기억하도록 만드는 대신, 답변에 필요한 지식을 외부에서 가져오게 하는 데 있어요.

RAG가 특히 잘 맞는 사례는 다음과 같아요.

- 자주 바뀌는 정책이나 제품 문서를 기준으로 답해야 할 때
- 사내 지식처럼 공개 model이 알 수 없는 자료를 사용해야 할 때
- 답변과 함께 원문 출처를 보여 줘야 할 때
- model을 다시 학습하지 않고 문서를 추가하거나 삭제해야 할 때

반대로 창의적인 문장 작성처럼 외부 사실이 중요하지 않은 작업에는 검색 단계가 불필요할 수 있어요. 적은 양의 고정된 정보를 항상 prompt에 넣을 수 있다면 RAG보다 단순한 구성이 더 낫기도 해요.

## 전체 동작 흐름

RAG는 문서를 준비하는 indexing 단계와 질문에 답하는 query 단계로 나눌 수 있어요.

| 단계 | 입력 | 처리 | 결과 |
| --- | --- | --- | --- |
| Indexing | 원본 문서 | 정제, chunking, embedding | 검색 가능한 index |
| Retrieval | 사용자 질문 | query 변환, 검색, metadata filter | 관련 chunk 후보 |
| Reranking | 질문과 후보 | 관련도 재평가 | 우선순위가 정해진 context |
| Generation | 질문과 context | prompt 구성, LLM 호출 | 근거가 포함된 답변 |

Indexing은 문서가 들어오거나 바뀔 때 실행해요. query 단계는 사용자가 질문할 때마다 실행해요. 두 흐름을 분리하면 문서 갱신 실패와 검색 실패, 생성 실패를 각각 관찰하기 쉬워져요.

단순화한 구조를 TypeScript로 표현하면 다음과 같아요. 특정 SDK에 의존하지 않도록 각 단계를 dependency로 분리한 예제예요.

```typescript {26-34}
type RetrievedChunk = {
  id: string;
  text: string;
  source: string;
  score: number;
};

type RagDependencies = {
  embed: (text: string) => Promise<number[]>;
  search: (input: {
    query: string;
    vector: number[];
    limit: number;
  }) => Promise<RetrievedChunk[]>;
  rerank: (query: string, chunks: RetrievedChunk[]) => Promise<RetrievedChunk[]>;
  generate: (input: {
    question: string;
    context: RetrievedChunk[];
  }) => Promise<string>;
};

export async function answerWithRag(
  question: string,
  dependencies: RagDependencies,
): Promise<string> {
  const queryVector = await dependencies.embed(question);
  const candidates = await dependencies.search({
    query: question,
    vector: queryVector,
    limit: 20,
  });
  const context = (await dependencies.rerank(question, candidates)).slice(0, 5);

  return dependencies.generate({ question, context });
}
```

핵심은 처음 검색한 결과를 전부 prompt에 넣지 않는다는 점이에요. 넓게 후보를 찾은 다음 reranking으로 관련도가 높은 문서만 추리고, 제한된 context 안에서 답을 만들어요.

## 문서를 검색 가능한 단위로 나누기

원본 문서를 통째로 embedding하면 질문과 직접 관련된 일부 문장이 긴 문서의 다른 내용에 묻힐 수 있어요. 반대로 지나치게 작게 나누면 제목, 조건, 예외처럼 답변에 필요한 문맥이 서로 떨어져요. 이 때문에 RAG 품질은 chunking 단계에서 이미 크게 결정돼요.

고정된 글자 수만 기준으로 자르기보다 문서 구조를 먼저 활용하는 편이 좋아요.

1. 제목과 section 경계를 기준으로 의미 단위를 나눠요.
2. 표와 code block처럼 함께 읽어야 하는 요소는 가능하면 유지해요.
3. 너무 큰 section만 token 수를 기준으로 한 번 더 나눠요.
4. 문맥이 경계에서 끊길 때만 필요한 만큼 overlap을 둬요.
5. 문서 ID, 제목, section, 작성일, 접근 권한을 metadata로 저장해요.

모든 문서에 통하는 하나의 chunk 크기는 없어요. FAQ처럼 질문과 답이 짧은 문서는 작은 chunk가 맞고, 계약 조항이나 장애 보고서는 앞뒤 조건을 함께 보존해야 해요. 실제 질문으로 Recall@k를 측정하면서 크기와 overlap을 조정해야 해요.

문서를 수정할 때는 오래된 chunk를 정확히 찾아 교체할 수 있어야 해요. 원본 문서의 식별자와 version, checksum을 함께 관리하면 중복 index와 삭제 누락을 줄일 수 있어요.

## Embedding과 vector search

Embedding model은 문장이나 문서를 숫자 vector로 바꿔요. 의미가 비슷한 문장은 vector 공간에서도 가까이 위치하도록 학습돼요. 질문과 각 chunk의 vector 유사도를 계산하면 같은 단어가 없어도 의미가 가까운 문서를 찾을 수 있어요.

Dense Passage Retrieval 연구는 질문과 passage를 각각 encoder로 변환하고 dense vector 유사도로 관련 문서를 찾는 방식을 보여 줬어요. RAG에서 사용하는 semantic search의 기반이 되는 접근이에요.

하지만 vector search만으로 모든 검색을 해결하기는 어려워요. 상품 코드, 오류 번호, class 이름처럼 정확한 문자열이 중요한 질문은 keyword search가 더 잘 맞을 수 있어요. 실무에서는 BM25 같은 lexical search와 vector search를 결합한 hybrid search가 안정적인 출발점이 돼요.

검색 범위를 줄일 수 있는 metadata도 중요해요. 예를 들어 사용자의 조직, 문서 언어, 제품 version, 공개 상태를 먼저 filter하면 관련도가 높아지고 권한이 없는 문서가 섞이는 문제도 줄일 수 있어요. 권한 filter는 검색 이후가 아니라 검색 query 자체에 적용해야 해요.

## Reranking과 context 구성

첫 retrieval은 빠르게 후보를 넓게 찾는 역할을 해요. 그다음 reranker가 질문과 각 후보를 함께 읽고 관련도를 다시 계산해요. 검색 단계에서 top 20을 가져온 뒤 상위 5개만 context로 사용하는 식이에요.

후보를 많이 넣는다고 답변이 항상 좋아지지는 않아요. 관련 없는 문서가 늘면 model이 잘못된 근거를 선택할 수 있고, token 비용과 latency도 커져요. 긴 context의 중간에 있는 정보를 model이 놓칠 수 있다는 연구도 있어요. 따라서 context window를 가득 채우기보다 답변에 필요한 근거만 남기는 편이 안전해요.

Context를 구성할 때는 다음 정보를 함께 전달하면 좋아요.

- 원문 내용과 안정적인 source ID
- 문서 제목과 section
- 작성일이나 version
- 답변에서 사용할 citation label

Prompt에는 주어진 context만 근거로 답하고, 근거가 부족하면 모른다고 말하도록 명시해요. 서로 충돌하는 문서가 검색되면 더 최신 문서를 무조건 고르기보다 충돌 사실과 각 출처를 함께 보여 주는 정책도 필요해요.

## RAG와 fine-tuning의 차이

RAG와 fine-tuning은 서로 대체하는 기술이 아니라 해결하는 문제가 달라요.

| 기준 | RAG | Fine-tuning |
| --- | --- | --- |
| 주된 목적 | 외부 지식을 찾아 답변에 반영 | model의 행동, 형식, 작업 방식을 조정 |
| 정보 갱신 | 문서와 index를 갱신 | 학습을 다시 실행 |
| 출처 제공 | 검색 문서를 citation으로 연결 가능 | 학습 data의 개별 출처 추적이 어려움 |
| 적합한 사례 | 사내 문서 검색, 최신 정책, 근거 기반 질의응답 | 고정된 출력 형식, 분류 방식, 특정 문체 |

최신 제품 정책을 답해야 한다면 RAG가 먼저예요. 일정한 JSON 형식이나 분류 기준을 model이 안정적으로 따르게 만들려면 fine-tuning이 더 직접적인 방법일 수 있어요. 두 방법을 함께 사용해 검색된 근거를 특정 형식으로 답하게 만들 수도 있어요.

## 품질을 어떻게 평가할까

최종 답변만 읽고 RAG 전체를 평가하면 원인을 찾기 어려워요. 검색과 생성을 나눠서 측정해야 해요.

Retrieval 단계에서는 정답 근거가 top k 안에 포함됐는지 확인하는 Recall@k나 Hit Rate가 기본 지표가 돼요. 순서까지 중요하면 MRR이나 nDCG를 볼 수 있어요. 이 단계가 실패했다면 prompt를 바꾸기보다 chunking, embedding model, filter, search query를 먼저 점검해야 해요.

Generation 단계에서는 다음 항목을 확인해요.

- 답변이 검색한 context로 뒷받침되는가
- 질문에 필요한 내용을 빠뜨리지 않았는가
- citation이 실제 근거와 연결되는가
- 근거가 없을 때 답변을 만들어 내지 않는가

RAGAS는 context relevance와 faithfulness처럼 retrieval과 generation을 나눠 평가하는 지표를 제안해요. 자동 평가는 반복 실험 속도를 높여 주지만, 업무상 중요한 질문은 사람이 검토한 test set도 함께 유지해야 해요.

정확도 외에도 p95 latency, 질문당 token과 검색 비용, 빈 검색 결과 비율을 관찰해야 해요. 품질이 비슷하다면 더 적은 chunk와 짧은 context로 답하는 구성이 운영하기 좋아요.

## 자주 발생하는 실패

RAG가 틀린 답을 만들었을 때 LLM부터 교체하면 원인을 놓치기 쉬워요. 실패가 발생한 단계를 먼저 구분해야 해요.

### 정답 문서를 찾지 못함

Chunk가 너무 크거나 작지 않은지, 문서 제목과 핵심 metadata가 embedding 대상에 포함됐는지 확인해요. 정확한 식별자가 중요한 질문이라면 keyword search를 결합하고, 사용자의 짧은 질문을 검색에 적합하게 확장하는 query rewriting도 검토할 수 있어요.

### 정답 문서를 찾았지만 답이 틀림

관련 없는 후보가 너무 많이 섞였는지, 중요한 근거가 context 중간에 묻혔는지 확인해요. Reranking과 context 순서를 조정하고, 답변마다 어떤 chunk를 사용했는지 trace를 남기면 원인을 찾기 쉬워져요.

### 오래된 정보로 답함

문서의 modified time과 version을 저장하고, 삭제되거나 바뀐 원문이 index에도 반영되는지 확인해요. Indexing pipeline은 추가뿐 아니라 수정과 삭제도 처리해야 해요.

### 권한이 없는 정보를 노출함

RAG의 검색 대상에는 private data가 들어갈 수 있어요. 사용자 권한을 metadata filter에 적용하고, cache key에도 권한 범위를 포함해야 해요. 문서 안의 명령을 system instruction처럼 따르는 prompt injection에도 대비해야 해요. 검색된 문서는 신뢰할 수 있는 명령이 아니라 참고 data로 취급하는 경계를 prompt와 application code에서 유지해야 해요.

## 구현 순서

처음부터 복잡한 agent나 여러 검색 전략을 붙이기보다 작은 baseline부터 만드는 편이 좋아요.

1. 실제 사용자 질문과 정답 근거 문서로 test set을 만들어요.
2. 문서 구조를 보존한 chunk와 metadata를 준비해요.
3. 하나의 embedding model과 vector search로 baseline을 만들어요.
4. Retrieval trace와 Recall@k를 측정해 검색 실패를 먼저 줄여요.
5. 정확한 문자열 검색이 필요하면 hybrid search를 추가해요.
6. 후보가 많아졌을 때 reranker를 붙여 최종 context를 줄여요.
7. 답변의 faithfulness와 citation 정확도, latency와 비용을 함께 비교해요.

RAG의 핵심은 LLM에 많은 자료를 넣는 데 있지 않아요. 질문에 필요한 근거를 정확히 찾고, 검증 가능한 형태로 전달하는 데 있어요. 좋은 RAG는 model보다 retrieval data와 평가 체계를 먼저 관리해요.
